# Phase4FY 補足調査: 「ボーナス確率」0件選別の妥当性 と RAG50 手法ギャップの解決

## 1. 「ボーナス確率について教えて」が0件選別になる件の結論

**結論: リグレッションではない。正しい/期待通りの挙動。**

### 検証手順
1. `entity_attribution.extract_query_entities("ボーナス確率について教えて")` は `["ボーナス確率"]` を正しく抽出。
2. 本番retrieverのembedding検索top-6のtitle・textいずれにも「ボーナス確率」という文字列は含まれない。
3. `retriever.get_all_chunks()` で実DB全119チャンクを対象にtitle・text両方を
   「ボーナス」という文字列で検索 → **0件ヒット**。実DB(スマスロ ミリオンゴッド-神々の軌跡、
   単一機種)には「ボーナス」という語を含むチャンクが1件も存在しない。
4. Phase4FUの`FU-A01`(同一テーマの実クエリ「ボーナス確率は設定によってどう変わりますか？」を
   実DBに対して**Phase4FY変更前の無加工A0パイプライン**でテスト済み)の記録を確認:
   - GT(`phase4fu_ground_truth.json` FU-A01)は `retrieval_sufficiency: "PARTIAL"`
     (青7連続・Z-ZONE関連の断片的示唆はあるが統一的な「ボーナス確率」表は存在しない、という
     GTの評価)
   - しかし実際のA0(無加工)応答は `"登録データにボーナス確率の設定差は見つかりませんでした。"`
     (`phase4fu_stage_b_base_generations.json` FU-A01) — `abstain_or_hedge: true`。
     つまり**Phase4FYの変更を一切加えていない、既存の本番パイプラインでさえ、この種の
     クエリに対しては断片情報を拾わず全面的にdeclineしていた**。

### 判断
Phase4FYのentity-attribution層を通した結果(0件選別 → 空context fallback →
「該当する構造化データ・解説文章は登録されていません」という既存jinja2テンプレートの
文言 → モデルは同様にdecline)と、変更前のA0の実際の挙動(全面decline)は
**質的に同じ出力**である。よって、この件はPhase4FYが新たに引き起こしたcompleteness
regressionではなく、実DBの内容そのものにある既知のギャップ(FU-A01で既に確認済み)を
そのまま反映しているに過ぎない。

なお `phase4fx_generation_results.json` の `P02`(「ボーナス確率について教えて」で
1/450〜1/280という具体的数値を含む応答)は、**RAG50の静的/架空contextプール**
(実DBに存在しない架空機種データ)に対するテスト結果であり、実本番DBとは無関係。
この混同を避けるため、次節でRAG50手法ギャップを明示的に解決する。

## 2. RAG50手法ギャップの解決方針(Section18 Stage F着手前の前提整理)

### 問題
RAG50の50probe(P02, P04, LC-08, Q15, Q17等含む)は、架空の複数機種
(機種A/C/FD/HH等)の静的JSON contextプールを前提に設計されている。実本番DBは
単一の実機種(スマスロ ミリオンゴッド-神々の軌跡)の119チャンクのみで構成されており、
RAG50の架空機種データは実DBには一切存在しない。そのため、Section18が要求する
「RAG50全50probeを実際の本番RAG経路(実retrieval)で再実行」は、字義通りには
実行不可能(架空機種名で検索しても実DBには何もヒットしない)。

### 採用する解決策
Stage F(Section18)を2つの独立したチェックに分割して実施する:

1. **RAG50プロンプト文字列を実本番経路に投入し、「架空データを捏造しないか」を検証する
   (安全性チェック)** — 50probe全てのプロンプト文字列をそのまま実本番RAGPipelineに通し、
   (a) 実DBに存在しない機種名・数値を生成しないこと、(b) 実DBの内容と矛盾する数値を
   生成しないこと、(c) 情報がない場合に正直にdeclineすること、を確認する。これは
   「RAG50が意図した通りの完全な補完テスト」ではなく、「entity-aware層が実DBという
   異なるコンテキストに対しても安全側に倒れるか」の**フェイルセーフ確認**として機能する。
   RAG50由来の8件の必須probe(P02/P04/LC-08/Q6/Q11/Q15/Q17/AD-04)を含む全件を対象とする。
2. **実DBに存在する同種の実データ(天井・ゲーム数・当選率など)を用いた「RAG50相当」の
   実機種版probeセットを新規に用意し、これを実本番経路の completeness regression
   チェックの主対象とする** — 例: P04(最低/最高設定の機械割差)相当として実DBに
   存在する「天井ゲーム数」「青7連続当選率」等の実問い合わせを使う。これはPhase4FXの
   `known_failure`/`phantom_entity`/`concept_binding`プローブ(実DB前提で設計済み)を
   Stage F相当の completeness チェックとして重点的に再利用することで多くを代替できる。

この方針は新しい研究や新しい設計判断ではなく、既存のPhase4FU/FX成果(実DBベースの
probeセット)を最大限再利用しつつ、RAG50固有の架空データ前提とのギャップを透明に
開示する運用上の対応である。Section18の記録(`phase4fy_rag50.json`)には、この方針と
両チェックの結果を明記する。

## 結論

- 「ボーナス確率」0件選別: **確認済み・正しい挙動・リグレッションではない**。
- RAG50手法ギャップ: **上記の2分割方式で対応することを決定**。Section18実施時に
  この方針に沿って `phase4fy_rag50.json` を作成する。
